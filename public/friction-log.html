Fanroute Live: friction logs

Amazon Developer Hackathon, Alexa+ track. Task attempted, steps, expected vs actual, severity, workaround and suggestion for each issue we hit, plus feature requests. Project: fanroute-live.vercel.app

1. Running a public MCP server as an Alexa+ add-on

  • Task: run Fanroute Live's MCP server inside Alexa+ and test it by voice.
  • Steps:
    1. Read the track resources.
    2. Found the Alexa+ add-on docs: the Alexa AI CLI (alexa-ai configure, alexa-ai new mcp, alexa-ai deploy), the web simulator, and the onboarding checklist.
  • Expected: a path for a public, no-login MCP server. Concert search needs no account.
  • Actual:
    • The onboarding checklist requires OAuth 2.1 account linking for every server: authorization code with PKCE (S256), RFC 9728 Protected Resource Metadata, and a 401 for unauthenticated requests. There's no documented option for tools that are public.
    • It also requires round trips under 500 ms. Our concert tool calls ListenBrainz and Ticketmaster, which can take longer on a cold call.
  • Severity: High for public or informational add-ons.
  • Workaround:
    • Built a web "Echo Show" host: an MCP client over Streamable HTTP plus the MCP Apps AppBridge, with browser speech in and out.
    • Checked interoperability with the MCP Inspector and with a spec 2025-11-25 client.
  • Suggestion:
    • An auth-optional add-on type for public tools.
    • A documented latency budget for tools that call external APIs, for example progress notifications, or a longer budget paired with a spoken "one moment".

2. MCP Apps views blocked from loading their SDK

  • Task: render the concerts and pledge cards as MCP Apps views inside the host's sandboxed iframe.
  • Steps: registered ui:// resources with registerAppResource. The view HTML loaded the ext-apps view SDK from a CDN.
  • Expected: the view SDK loads like any script.
  • Actual:
    • The host's default sandbox CSP blocks external scripts, so the view never connected.
    • The SDK's package.json isn't exported, so build tooling can't locate the browser bundle by path.
  • Severity: Medium.
  • Workaround: a build step (scripts/vendor-app-sdk.mjs) resolves @modelcontextprotocol/ext-apps/app-with-deps via import.meta.resolve and inlines the bundle (~400 KB) into each view.
  • Suggestion:
    • Ship a small, documented "view runtime" bundle meant to be inlined.
    • Export package.json.
    • Say in the docs that views must be self-contained under the default CSP.

3. Confirming spec 2025-11-25 compatibility

  • Task: prove the server meets the track's "spec 2025-11-25 or later, Streamable HTTP" rule.
  • Steps: built on the v2 TypeScript SDK (createMcpHandler). Tested with both the v2 client and a v1 client that speaks 2025-11-25.
  • Expected: a compatibility table, or a conformance checker, saying which SDK versions satisfy the requirement.
  • Actual: we had to test the version negotiation ourselves with two clients.
  • Severity: Low.
  • Workaround: scripts/mcp-check.mts runs both clients against production.
  • Suggestion: a hosted conformance check (enter a URL, get pass or fail for the protocol revision, the transport and the tool schemas) linked from the track page.

4. Mounting an MCP handler in Next.js 16

  • Task: serve the MCP endpoint from a Next.js route on Vercel.
  • Steps: added the usual export const runtime and dynamic route config next to the handler.
  • Expected: a normal serverless route.
  • Actual: with cacheComponents enabled, Next.js rejects route-segment config. That isn't obvious when you follow typical MCP server examples.
  • Severity: Low.
  • Workaround: removed the segment config. The stateless handler works without it.
  • Suggestion: a "deploy an MCP server on Vercel / Next.js" example in the MCP SDK docs or the track resources.

Feature requests

  • Critical: auth-optional Alexa+ add-ons for public MCP tools, plus guidance for tools that call slow third-party APIs (see friction log 1). It's the biggest blocker to shipping informational add-ons.
  • Important: device hints in the MCP Apps host context (screen size, voice-only device vs Echo Show). A server could then choose between a spoken summary and a card without guessing.
  • Nice-to-have: a convention for a short "speak this" field in tool results. We return a speech string that's separate from the card data, and a standard name would let any voice host use it.
